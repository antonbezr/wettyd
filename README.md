# wettyd

wetty's browser frontend, running on ttyd's C/libwebsockets backend.

## Why

[wetty](https://github.com/butlerx/wetty) is a Node.js server that spawns
`ssh`/`login` via `node-pty` and talks to the browser over Socket.IO.
[ttyd](https://github.com/tsl0922/ttyd) is a small C server (libwebsockets +
libuv) that spawns any command via a PTY and talks to the browser over a
single raw WebSocket, with no HTTP long-polling fallback.

In practice, wetty's Socket.IO client can end up stuck on HTTP long-polling
instead of upgrading to a real WebSocket, which adds a full HTTP
request/response round trip per keystroke, noticeable as typing lag,
especially over a real network path (e.g. behind a reverse tunnel). ttyd's
backend has no such fallback: it's always a single persistent WebSocket.

wettyd keeps wetty's nicer, more featureful frontend (onscreen mobile
keyboard, xterm options editor, file-download detection, clipboard/web-links
addons, fontawesome UI) and puts it on top of ttyd's backend instead, by
reimplementing the small transport-facing slice of wetty's client to speak
ttyd's native binary WebSocket protocol.

## What's reused from each project

- **Backend (`src/`, `cmake/`, `CMakeLists.txt`, `man/`)** - ttyd's C source,
  essentially unmodified (cosmetic `wettyd`-branding string changes only).
  `src/html.h` is regenerated by the frontend build (see below) instead of
  ttyd's own preact-based frontend.
- **Frontend (`frontend/src/client/`, `frontend/src/assets/`)** - wetty's
  TypeScript client, esbuild build, xterm.js configuration, styling, mobile
  keyboard, file-download detection (`wetty/download.ts`), and the xterm
  options editor (`assets/xterm_config/`), copied from wetty largely as-is.
- **New code** - `frontend/src/client/wetty/ttydSocket.ts` is a from-scratch
  transport adapter implementing ttyd's binary WS protocol (modeled on ttyd's
  own `html/src/components/terminal/xterm/index.ts`, both MIT licensed)
  behind the same small `on()`/`emit()` interface wetty's `wetty.ts`/`term.ts`
  already expected, those two files needed only minimal changes. wetty's own
  server-side flow-control ack protocol (`socket.emit('commit', ...)`) doesn't
  apply against a ttyd backend, so `wetty.ts`'s data handler now uses ttyd's
  simpler client-side pause/resume heuristic instead (see
  `frontend/build.js` and `wetty.ts` for the exact numbers, taken from ttyd's
  `html/src/components/app.tsx`).
- **Dropped** - wetty's PWA/service-worker (`sw.js`, `manifest.json`) and its
  Node server (`express`, `socket.io`, `node-pty`, SSH plumbing) entirely,
  since ttyd's backend serves one self-contained HTML blob and spawns the
  configured command directly via `node-pty`'s C equivalent (ttyd's own
  `pty.c`), no SSH hop needed.

## How the build works

ttyd embeds its entire frontend as a gzip-compressed byte array baked into
`src/html.h` (see `html/gulpfile.js` upstream) and serves it as one HTTP
response with no other static routes. `frontend/build.js` reproduces that
pipeline against wetty's frontend instead of ttyd's:

1. `esbuild` bundles `frontend/src/client/wetty.ts` (+ its Sass) into a single
   IIFE `wetty.js` / `wetty.css`.
2. The xterm options editor (`assets/xterm_config/`) and the favicon are
   inlined by hand into `frontend/src/template.html`'s placeholders (a
   `srcdoc` iframe and a `data:` URI, respectively, both fully static, no
   server route needed).
3. [`inline-source`](https://www.npmjs.com/package/inline-source) inlines the
   bundled JS/CSS into that template, producing one self-contained
   `frontend/build/index.html`.
4. That file is gzipped and written out as `src/html.h` in ttyd's exact
   format, ready for the C build to embed.

## Building

```sh
# 1. Frontend -> src/html.h
cd frontend
npm install
npm run build

# 2. C backend (needs cmake, libwebsockets, libuv, json-c, zlib, e.g. via
#    `brew install cmake libwebsockets libuv json-c` on macOS)
cd ..
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . -j4
```

The build runs the test suite automatically as part of that last step, and
fails if any test fails. To run it again on demand without rebuilding:

```sh
cd build && ctest --output-on-failure
```

`tests/test_auth.c` is pure C unit tests for `src/auth.c`, no server, no
sockets. `tests/test_auth_protocol.py` is a protocol-level test that spawns
a real `wettyd` process and drives the WS wire protocol directly, checking
the actual bytes sent, not just the underlying decision logic.

## Running

Same CLI as ttyd (see `./build/wettyd --help`), **ttyd is read-only by
default**, pass `-W`/`--writable` or nothing you type will reach the shell:

```sh
./build/wettyd --writable --port 7681 bash
```

Then open `http://localhost:7681/`.
